# 宝くじ分析ラボ — PWA版

ロト6・ロト7の出現傾向を可視化し、番号を生成するインストール型Webアプリ。
GitHub Pages に置けば、**当せん番号が週2回、自動で最新に更新されます。**

---

## 公開のしかた（GitHub の web 画面だけで完結・所要15分）

コマンドや git のインストールは不要です。ブラウザだけで公開できます。

### 0. 前提: リポジトリは Public にする

**GitHub Free では、Pages を使うにはリポジトリが Public である必要があります。**
Private リポジトリから公開できるのは GitHub Pro / Team / Enterprise のみです。

このアプリは公開されて困る情報を含みません（当せん履歴やマイ番号は
利用者のブラウザ内にだけ保存され、リポジトリには入りません）。

### 1. リポジトリを作る

[github.com/new](https://github.com/new) を開き、

- **Repository name**: 例 `loto-lab`（この名前がURLに入ります）
- **Public** を選択
- **Add a README file** に**チェックを入れる**（空だとファイルを追加しづらいため）

**Create repository** を押します。

### 2. アプリ本体をアップロード

リポジトリの **Add file → Upload files** を開き、
zip を展開した `loto-lab-pwa` フォルダの**中身**をドラッグ&ドロップします。

アップロードするもの:

```
index.html   sw.js   manifest.webmanifest   icon-192.png   icon-512.png
.nojekyll    ← 重要（後述）
data/  （フォルダごと）
tools/ （フォルダごと）
```

> **`.nojekyll` は必ず入れてください。** 空のファイルですが、これが無いと
> GitHub Pages は Jekyll というブログ生成ツールを通してサイトを組み立てようとし、
> 失敗するとサイト全体が404になります。このファイルを置くと Jekyll を完全に
> バイパスし、ファイルをそのまま配信します。ドット始まりで見えない場合は、
> 手順3と同じ **Add file → Create new file** でファイル名に `.nojekyll` と
> 入力し、中身は空のまま Commit すれば作れます。

**フォルダごとではなく中身を置いてください。**
`loto-lab-pwa` フォルダごと入れると URL が
`…github.io/loto-lab/loto-lab-pwa/` と一段深くなります。

下部の **Commit changes** を押します。

> `.github` フォルダはここでは**アップロードできません**（次の手順で作ります）。
> ドット始まりのフォルダは macOS の Finder や Windows のエクスプローラーで
> 非表示になっており、ドラッグ&ドロップでは取りこぼされます。

### 3. ワークフローを web 画面で作る

自動更新の設定ファイルは、パスを直接入力して作ります。

1. **Add file → Create new file** を開く
2. ファイル名の欄に次を**そのまま入力**します（`/` を打つとフォルダが自動でできます）

   ```
   .github/workflows/update-loto.yml
   ```

3. zip 内の `.github/workflows/update-loto.yml` をテキストエディタで開き、
   **中身を全部コピーして貼り付け**
4. **Commit changes** を押す

### 4. Pages を有効にする

**Settings** タブ → 左サイドバー「Code and automation」の **Pages** →
「Build and deployment」の **Source** で **Deploy from a branch** を選び、
Branch を **main** / **/ (root)** にして **Save**。

数分後、同じ画面の上部に公開URLが出ます。

```
https://<ユーザー名>.github.io/<リポジトリ名>/
```

### 5. 当せん番号を取り込む

**Actions** タブ → 左の **当せん番号の自動更新** → 右の **Run workflow** →
緑の **Run workflow** ボタン。

3〜5分で完了し、`data/loto6.json` と `data/loto7.json` に当せん番号が入ります。
以降は火・金・水・土の朝に自動で実行されます。

> Actions タブで「Workflows aren't being run on this forked repository」等が出る場合は、
> **I understand my workflows, go ahead and enable them** を押してください。

### 6. スマホでアプリとして入れる

公開URLをスマホで開き、
iPhone は共有ボタン →「ホーム画面に追加」、
Android はメニュー →「アプリをインストール」。

### うまくいかないとき

| 症状 | 原因と対処 |
|---|---|
| Settings に Pages が無い | リポジトリが Private になっている。Settings 最下部の Danger Zone →「Change repository visibility」で Public に変更 |
| 404 が出る | 反映に数分かかります。URL 末尾の `/` を忘れていないかも確認 |
| 画面は出るがデータが空 | 手順5のワークフローをまだ実行していない。または失敗している（Actions タブで赤い×を確認） |
| ワークフローが `Permission denied` / 403 で失敗 | **Settings → Actions → General → Workflow permissions** で **Read and write permissions** を選んで Save し、再実行 |
| ワークフローが取得に失敗する | みずほ側の一時的な遮断や形式変更の可能性。`data/` は書き換えられないので、アプリは直前のデータのまま動きます。自動でIssueが立ちます |

## 過去データを増やす（さかのぼり取得）

みずほの目次CSVには**直近1年ぶんしか載っていません**（ロト6で約112回、ロト7で約56回）。
それより古い回も回別CSVは公開されているので、後から取りに行けます。
履歴が増えると「戦略の検証」の精度が上がります。

**Actions タブ → 「過去データの取り込み（手動）」 → Run workflow**

入力欄が3つ出ます。

| 項目 | 意味 | おすすめ |
|---|---|---|
| back | 何回さかのぼるか | `300` |
| limit | 1回の実行で取得する上限 | `300` |
| game | 対象 | `both` |

**繰り返し実行すると、そのたびにさらに過去へ進みます。**
起点は「手元にある最古の回」なので、`300` のまま3回押せば約900回ぶんさかのぼります。

公開されていない回に達すると自動で打ち切られ、「これ以上さかのぼれない可能性があります」と
表示して正常終了します（エラーにはなりません）。

所要時間は300回で3〜5分ほど。通常の自動更新とは別のワークフローなので、
普段の動作には影響しません。

## 自動更新の仕組み

```
① 目次CSV   .../loto6/csv/loto6.csv        回号と抽せん日の一覧（本数字は入っていない）
        ↓  手元に無い回号だけを洗い出す
② 回別CSV   .../loto6/csv/A1022124.CSV     「本数字,06,20,29,36,37,41,ボーナス数字,19」
        ↓  GitHub Actions（火・金・水・土 の朝8:10 JST）
  tools/update-loto.mjs が取得・解析・既存データとマージ
        ↓  変更があれば data/*.json をコミット
  GitHub Pages が配信
        ↓  fetch('./data/loto6.json')  ← 同一オリジンなのでCORSの問題なし
  アプリが起動時に差分を取り込む
```

みずほの配信は2段構成です。`loto6.csv` は**回号と抽せん日の目次**で、本数字は含みません。
本数字は回ごとの `A102{回号4桁}.CSV`（ロト7は `A103{回号4桁}.CSV`）にあります。
そのため目次で回号を把握し、**手元に無い回だけ**を回別CSVから取りに行きます。
2回目以降の実行は新しい1〜2回分だけなので、20秒ほどで終わります。

**なぜアプリから直接みずほを読まないのか**

- ブラウザの CORS 制限により、静的サイトの JavaScript から `mizuhobank.co.jp` は読めません
- 公式CSVは Akamai の bot 対策があり、通常のリクエストでは弾かれることがあります

そのため「取得は GitHub Actions（サーバー側）、配信は同一オリジン」という形にしています。
素の `fetch` が弾かれた場合は Playwright（実ブラウザ）に自動フォールバックします。

**壊れたデータをコミットしない設計**

次のいずれかに当てはまると、スクリプトは `data/` を書き換えずに終了コード1で失敗します。

- 目次CSVから回号を1件も読み取れなかった（＝みずほ側の形式変更の可能性）
- 回別CSVを1件も取得できなかった
- 半数以上の回で抽せん日を読み取れなかった
- マージ後の件数が既存より減った

失敗時は取得した生データの先頭数行をログに出すので、形式が変わった場合も原因がすぐ分かります。

失敗時は自動で Issue が立つので気づけます。アプリは直前のデータのまま動き続けます。

## ローカルでの実行

```bash
cd tools
npm install                    # Playwright フォールバック用（任意）
npx playwright install chromium

node update-loto.mjs --dry-run # 書き込まずに動作確認
node update-loto.mjs           # data/*.json を更新
node update-loto.mjs loto6     # ロト6だけ
node update-loto.mjs --limit 30   # 1回の実行で取りに行く上限（既定150）
node update-loto.mjs --back 200   # 目次より古い回もさかのぼって取得

node test-parser.mjs           # 取り込みパーサの回帰テスト（61件）
node test-app.mjs              # index.html のロジック検証（49件）
node test-fetch.mjs            # 取得フロー全体の検証・通信はモック（9件）
node test-backfill.mjs         # さかのぼり取得の検証・通信はモック（5件）
```

アプリの動作確認は、`file://` ではなく HTTP サーバー経由で開いてください
（`file://` では Service Worker と自動取得が動きません）。

```bash
python3 -m http.server 8000    # → http://localhost:8000/
```

## 更新するときの注意

`index.html` などを修正したら、**`sw.js` の `APP_VERSION` を必ず上げてください。**

```js
const APP_VERSION = 'v2.1.1';   // ← 上げる
```

HTML はネットワーク優先で取得する設計なので通常はすぐ反映されますが、
アイコンなどのアセットはキャッシュ優先のため、版を上げないと古いままになります。

## v2 での修正内容

前バージョンから、データが静かに壊れる不具合を中心に修正しています。

### 重大

| 修正 | 内容 |
|---|---|
| Service Worker の更新戦略 | キャッシュ名が `v1` 固定で、再アップロードしても**古い画面が永久に表示されていた**。版数管理 + HTMLはネットワーク優先に変更 |
| ゲーム取り違えの検出 | ロト7のCSVをロト6タブで読ませると、無警告で7個中6個だけ取り込み**データが丸ごと汚染されていた**。取り込み前に警告を出すよう変更 |
| 回号の混入 | `12,3,11,19,25,31,40,5` のようなCSVで回号が本数字に混ざっていた。ファイル全体の列プロファイルから本数字ブロックを特定する方式に書き直し |
| デモデータの誤爆 | 確認なしで既存履歴を全消去していた。履歴がある場合は必ず確認する |
| 入力テキストの消失 | データタブで番号をタップすると、貼り付けた取り込みテキストが消えていた。state に保持するよう変更 |

### 統計・ロジック

| 修正 | 内容 |
|---|---|
| カイ二乗検定の自由度 | 非復元抽出なので `E[χ²] = max − pick`。`df = max − 1` は誤りで、**偽陽性率が1.1%（本来5%）まで落ち偏りを検出できなかった**。`df = max − pick` に修正し、シミュレーションで3.9%まで回復を確認 |
| 和暦の日付 | `令和8年5月30日` / `R8.5.30` を読めず日付が空になり、「ご無沙汰番号」が壊れていた。西暦・和暦の両方に対応。公式CSVは和暦なので必須の修正 |
| 「不人気ねらい」の連番 | 連番を**減点**していたが、連番は人が選ばない＝被りにくいので目的と逆。加点に変更 |
| マイ番号の照合範囲 | 全履歴と照合するため「過去にその組合せが出た」だけで当選表示になっていた。登録日以降の抽せんのみ照合するよう変更 |
| JSON取り込みの検証 | `[5,5,5,5,5,5]` のような重複番号を受け入れていた。弾くよう修正 |
| 回号の保存 | 回号を保持し、重複判定とマージの精度を向上 |

### その他

- 保存失敗（容量超過など）を握り潰さず警告するよう変更
- `maximum-scale=1` を削除しピンチズームを解放（アクセシビリティ）
- CSV書き出しでボーナス列がずれる問題を修正
- 履歴ソートの比較関数が等値で `0` を返していなかった問題を修正
- Google Fonts を非同期読み込みにし、オフライン時はシステムフォントにフォールバック
- 分析結果をキャッシュし、再描画のたびの再計算をやめた
- 履歴リストのスクロール位置が再描画で戻る問題を修正

## v2.1 で追加した機能

### 履歴の編集

各履歴行の ✎ ボタンから、**回号・抽せん日・本数字・ボーナス数字**をその場で修正できます。
本数字が規定の個数そろうまで保存ボタンは無効。回号が他の回と重複する場合は確認が出ます。
削除→再入力が不要になりました。

### 分析タブに「詳細」と「戦略の検証」

分析タブ上部のチップで3つのビューを切り替えます。

**詳細** — よくある思い込みを理論値と突き合わせて検証します。

| 項目 | 内容 |
|---|---|
| 連番はどのくらい出るか | ロト6は約**54.7%**、ロト7は約**74.5%**の回で連番が出ます（理論値。モンテカルロ20万回で54.51%と一致を確認）。「連番は出ない」は誤り |
| 前回と何個かぶるか | 超幾何分布の理論値と比較。平均 pick²/max（ロト6なら0.837個）が理論値 |
| 下一桁の分布 | 1〜43では下一桁ごとに個数が違うため理論値も一定でない点を反映 |
| よく一緒に出た数字ペア | 上位10組。全903通りあるので上位が平均を超えるのは当然、という説明付き |

各項目は実測（棒）と理論値（縦線）を重ねて表示し、ずれが何標準偏差かを自動で判定します。

**戦略の検証** — 5つの生成戦略のバックテスト。

履歴の**前半70%だけで傾向を学習し、後半30%で採点**します（学習に使った回で採点する自己参照を避けるため）。
各戦略300口を生成し、検証期間の全抽せんと照合。結果は理論値 pick²/max と並べて表示します。

誤差の計算には注意点があります。**標準誤差は口数ではなく検証に使えた抽せん回数で決まります。**
同じ戦略の口は似た番号を持つため、口数を増やしても検証期間の偏りは打ち消せません。
そのため抽せんごとの平均のばらつきから標準誤差を求めています
（「不人気ねらい」は番号帯が偏るぶん誤差が大きく出ます。これは正しい挙動です）。

また5戦略を同時に比較するため、単純な2σ判定では公正なデータでも約27%が誤警報になります
（実測）。多重比較を考慮し**2.6σ**をしきい値にしています（誤警報率およそ6%）。

結論の文言は決め打ちではなく、実測したσから分岐します。

## v2.2 で追加した機能

### 買う番号の診断

「マイ番号」タブで数字を選ぶと、その組み合わせのカルテが表示されます。登録しなくても、
選んだ時点ですぐ出ます。登録済みの番号は 🔍 ボタンからいつでも診断できます。

**選んだ数字のこれまで** — 数字ごとに、出現回数・理論値・最後に出てから何回前か・最終出現の回号と日付。

| 数字 | 出現 | 理論値 | 最後に出てから | 最終出現 |
|---|---|---|---|---|
| 3 | 20回 | 16.7回 | 3回前 | 第2116回 2026.03.26 |
| 19 | 23回 | 16.7回 | 前回 | 第2119回 2026.04.16 |

**過去の抽せんと何個一致したか** — その組み合わせを全履歴と突き合わせ、0個〜全個一致が
それぞれ何回あったかを理論値（超幾何分布）と並べて表示します。最高一致数、3個以上一致した回数、
完全一致の有無も出ます。

**近かった回** — 3個以上一致した回を一致数の多い順に最大6件。一致した数字を金色で示すので、
どこがかすったのかが一目で分かります。

**選んだ数字どうしの組み合わせ** — 選んだ数字から作れる全ペアについて、一緒に出た回数を理論値と比較。

**組み合わせの形** — 合計値・奇数の個数・低い数の個数・連番の有無を、過去の平均と並べて表示。

いずれも「過去にどうだったか」の記録であり、次回の当たりやすさとは無関係です。
各カードにその旨と、根拠となる確率（1つの数字が出る確率、ペアが揃う確率、
組み合わせの当せん確率 6,096,454分の1）を明記しています。

### その他

- 出現ヒートマップを単一色相の逐次ランプに変更（旧版は青→金の2色相で、大きさの表現として不適切だった）
- グラフのデータ色を検証済みの配色に変更（`#b18827` / `#329acd` — 色覚多様性でのΔE 21.6、背景コントラスト3:1以上）。凡例を常時表示し、値は必ず数値でも直接ラベルするので色だけに依存しません
- 分析結果のキャッシュが件数と末尾IDだけをキーにしていたため、**編集しても再計算されない**不具合を修正
- `tools/test-app.mjs` を追加。関数の欠落・未処理アクション・過去の修正の退行を自動検出します

- 抽選は毎回独立した完全ランダムであり、過去の傾向から次回を予測することはできません
- **当せん確認は必ず [みずほ銀行公式](https://www.mizuhobank.co.jp/takarakuji/check/loto/index.html) で行ってください**

- 当せん番号データの出典: みずほ銀行
